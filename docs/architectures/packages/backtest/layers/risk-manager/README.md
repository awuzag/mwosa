# RiskManager

`RiskManager`는 주문 후보가 계좌 전체 관점에서 허용 가능한지 검사한다. 전략이 좋은 신호를 만들더라도 계좌 위험이 과도하면 주문을 막거나 줄여야 한다.

## 핵심 질문

이 위험을 받아도 될까?

## 책임

- 주문 후보를 승인, 거절, 축소한다.
- 종목, 전략, 계좌 단위의 위험 한도를 적용한다.
- 일일 손실 한도와 최대 낙폭 기반 중단 조건을 관리한다.
- 리스크 판단 이유를 로그와 리포트에 남긴다.

## 입력

- 주문 후보
- 현재 포트폴리오
- 현재 및 예상 포지션 비중
- 손실 한도와 리스크 설정
- 최근 거래 및 손익 이력

## 출력

- 승인된 주문
- 축소된 주문
- 거절된 주문과 사유
- 리스크 이벤트

## 구현 후보

- 직접 구현: `RiskPolicy`, `RiskDecision`, 정책 체인 구조는 시스템 안전성의 핵심이므로 직접 구현해야 한다.
- [shopspring/decimal](https://github.com/shopspring/decimal): 계좌 금액, 비중, 손실 한도를 정확하게 계산하기 위한 후보.
- [go-playground/validator](https://github.com/go-playground/validator): 리스크 설정 파일의 필수값과 허용 범위 검증에 사용할 수 있다.
- [Watermill](https://watermill.io/): 리스크 이벤트를 비동기 이벤트로 발행하거나 감사 로그 파이프라인으로 넘길 때 조사할 후보.

## 조사할 자료

- 터틀 트레이딩의 시장별, 전체 계좌별 위험 제한
- 종목당 최대 비중, 전략당 최대 비중, 전체 노출 한도
- 미국 ETF 자산군, 섹터, 국가, 운용사 쏠림 위험 측정 방식
- 일일 손실 제한, 연속 손실 제한, MDD 기반 거래 중단 규칙
- 실거래 주문 전 수동 승인 모드 설계

## 설계 쟁점

- 리스크 규칙을 순차적으로 적용할지, 점수화 또는 정책 체인으로 적용할지 정해야 한다.
- 주문 축소가 가능한 규칙과 무조건 거절해야 하는 규칙을 구분해야 한다.
- 백테스트와 실거래에서 같은 리스크 규칙을 재사용할 수 있어야 한다.
- 리스크 거절이 전략 성과에 어떤 영향을 줬는지 리포트로 추적해야 한다.
