# Portfolio

`Portfolio`는 현재 계좌 상태를 표현한다. 전략이 계좌를 직접 바꾸지 않고, 체결 결과만 포트폴리오에 반영되는 구조가 되어야 한다.

## 핵심 질문

지금 계좌는 어떤 상태인가?

## 책임

- 현금, 보유 종목, 평가 금액을 관리한다.
- 체결 결과를 반영해 포지션을 갱신한다.
- 실현 손익과 미실현 손익을 계산한다.
- 리스크 규칙과 리포터가 참조할 계좌 상태를 제공한다.

## 입력

- 초기 현금
- 체결 결과
- 현재 시장 가격
- 수수료와 세금
- 포지션 메타데이터

## 출력

- 현금 잔고
- 보유 포지션 목록
- 총자산
- 종목별 비중
- 실현 손익과 미실현 손익
- 거래 내역

## 구현 후보

- 직접 구현: 포지션, 체결 반영, 평균 매수가, 실현손익 계산은 도메인 규칙이므로 직접 구현해야 한다.
- [shopspring/decimal](https://github.com/shopspring/decimal): 현금, 평가금액, 손익 계산에서 decimal 기반 금액 타입 후보.
- PostgreSQL: 페이퍼 트레이딩과 실거래의 포트폴리오 상태, 체결 내역, 감사 로그를 저장하는 기본 운영 저장소.
- [modernc.org/sqlite](https://pkg.go.dev/modernc.org/sqlite): 로컬 실험과 작은 백테스트 결과를 저장할 때의 보조 후보.
- [DuckDB Go](https://duckdb.org/docs/stable/clients/go): 거래 내역과 성과 분석을 함께 조회해야 할 때 조사할 분석형 저장소 후보.
- [Watermill](https://watermill.io/): 포트폴리오 상태 변화를 이벤트로 남기고 재생하는 구조를 실험할 때 후보.

## 조사할 자료

- 미국 ETF 매매 비용, 환율, 세금 반영 방식
- 평균 매수가 계산 방식
- 부분 매도와 전량 매도 시 손익 계산
- 미국 주식/ETF 결제 구조를 초기 모델에 반영할지 여부
- 브로커 실계좌 잔고와 가상 포트폴리오를 동기화하는 방식

## 설계 쟁점

- 초기에는 단순 현금 정산 모델로 시작하고, 결제 지연은 나중에 반영할 수 있다.
- 포트폴리오는 판단하지 않고 상태만 제공해야 한다.
- 백테스트 재현을 위해 모든 체결과 상태 변화는 이벤트로 남기는 편이 좋다.
- 실거래에서는 브로커 계좌 상태와 내부 포트폴리오 상태가 어긋날 수 있으므로 동기화 규칙이 필요하다.
