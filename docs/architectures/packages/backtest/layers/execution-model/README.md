# ExecutionModel

`ExecutionModel`은 백테스트와 페이퍼 트레이딩에서 주문이 어떤 가격과 수량으로 체결됐다고 볼지 결정한다. 실제 주문 송신은 `OrderExecutor`의 책임이다.

다중 타임프레임 전략에서는 [타임프레임 설계](../../timeframes/README.md)에 따라 실행 타임프레임을 기준으로 체결 가능성과 슬리피지를 판단한다.

## 핵심 질문

어떻게 체결됐다고 볼까?

## 책임

- 가상 체결 가격과 수량을 계산한다.
- 수수료, 세금, 슬리피지를 반영한다.
- 거래 가능 시간, 유동성 부족, 넓은 스프레드 같은 체결 불리 조건을 처리한다.
- 백테스트 결과에 체결 가정을 명시할 수 있게 한다.

## 입력

- 주문 후보
- 시장 데이터
- 체결 모델 설정
- 티커별 거래 가능 상태
- 수수료와 세금 설정
- 실행 타임프레임 데이터

## 출력

- 가상 체결 결과
- 체결 실패 사유
- 슬리피지와 거래 비용
- 체결 가정 메타데이터

## 구현 후보

- 직접 구현: 다음 시가 체결, 종가 체결, 거래량 제한, 스프레드와 슬리피지 같은 체결 모델은 미국 ETF 조건에 맞게 직접 구현해야 한다.
- [shopspring/decimal](https://github.com/shopspring/decimal): 체결 금액, 수수료, 세금, 슬리피지 계산의 정밀도 확보 후보.
- [Gonum](https://github.com/gonum/gonum): 확률적 슬리피지나 시뮬레이션 모델을 실험할 때 쓸 수 있는 수치 계산 후보.
- [cinar/indicator](https://github.com/cinar/indicator): 체결 모델 자체보다는 변동성 기반 슬리피지 가정을 만들 때 참고할 수 있다.

## 조사할 자료

- 미국 ETF 수수료, 세금, 환율, 정산 구조
- 정규장, 프리마켓, 애프터마켓의 체결 품질 차이
- 다음 시가, 당일 종가, VWAP, 거래량 제한 체결 모델
- 분봉 백테스트에서 체결 순서와 intra-bar ambiguity 문제
- 낮은 유동성, 넓은 스프레드, 장외 시간 주문 처리 방식

## 설계 쟁점

- 단순 모델과 보수적 모델을 모두 제공해야 한다.
- 분봉 하나 안에서 고가와 저가 중 무엇이 먼저 발생했는지 알 수 없는 문제가 있다.
- 실행 타임프레임을 더 낮추면 체결 가정은 정교해지지만 데이터 비용과 복잡도가 커진다.
- 거래량 기반 부분 체결을 언제부터 모델링할지 정해야 한다.
- 체결 가정을 바꿨을 때 리포트가 전략 성과 변화를 비교할 수 있어야 한다.
